Track M production method (owner ruling, 2026-10-14; evidence in `outputs/blackmoor-decomp/M0-binary-census-report.md`). Original x86 functions may be reconstructed as tool-assisted assembly: the project-owned generator (packet M03) emits Intel-syntax GNU assembly for one function from the owner's local original, an implementer annotates it (function and label names, frame and field symbols, the Track N source it corresponds to, unverified branches), and an independent reviewer confirms that the annotated source reassembles byte-exactly with the pinned `i686-w64-mingw32-as` 2.43.1 before the function counts. Such functions carry the class `tool_assisted_reconstructed_assembly`, reported separately from `explicit_reconstructed_assembly_source`; neither class claims original C++ or compiler provenance. Permitted encodings are mnemonics plus the `{load}`/`{store}` and `{disp8}`/`{disp32}` prefixes, the `.d8`/`.d32` branch suffixes, and `.insn` only in the five spellings listed in section 5 of the M0 report (16-bit and 32-bit accumulator immediates, the `DC C0` x87 form and `81 /x` word immediates); with those, the census reproduces 100% of the code bytes, so no other byte directive is permitted in code. Owner rulings of 2026-10-14 refine this: (1) jump and switch index tables, and only those, may be written as `.byte` lists in the `.s`, in a data item labeled `IDXTAB_<va>` whose comment names the owning function and the switch jump (`index table of FUN_<va> for the switch jump at 0x<va>`); the auditor enforces the label, and no other byte list is permitted. (2) Annotation requires named symbols for every register-relative displacement, frame (`[ebp±n]`), stack (`[esp+n]`) and object-field (`[reg+n]`); absolute addresses stay numeric. (3) The assembler is pinned by its version line (`GNU assembler (GNU Binutils) 2.43.1`) plus a self-test that reassembles a fixed source and must reproduce the expected bytes exactly, not by the SHA-256 of one machine's binary. (4) Owner ruling of 2026-10-15 (decision card on the planning thread): machine-generated names (`fn_<va>`, `arg_8`, `local_4`, `field_2c`, callee names from the index, the Track N link from the ledger) are valid annotation; they are written only by `scripts/annotate_machine.py` under an `# annotation:  machine` header, `annotate_machine.py check` must regenerate them identically, and a human-reviewed function drops the header and passes the hand-annotation audit instead. (5) Owner ruling of 2026-10-16 (decision card on the planning thread, "Count the last 22 code fragments as matched when they reassemble byte for byte?"): a code fragment counts as matched when it reassembles byte for byte with the pinned assembler, either as a function ending in a never-returning call, or bound together with the range it falls through into. Implemented through the second option for every such fragment, because a callee that never returns cannot be proven from the bytes (6 of the 13 call-ending fragments call `__fload_withFB`, which does return): the header declares `# ending:  call-end` (the code part's last instruction is a `call` with no data after it) or `# ending:  fall-through into <va>`, the auditor derives the ending from the original and requires header and manifest to agree, and the composer refuses the fragment unless the range that follows it is bound as code too. Neither ending claims original C++ or compiler provenance. (6) Owner ruling of 2026-10-19 (decision card on the planning thread, "Count rebuilt data and resources as matched when they reassemble byte for byte?", answered Yes): initialized data (`.rdata`, `.data`) and resource payloads count as matched when they are rebuilt as labeled assembler data directives with machine-generated names and reassemble byte for byte with the pinned assembler. `scripts/data_asm.py` emits them from the owner's local original (`asm_data/data-NNN.s` with a manifest and an audit report), `data_asm.py audit` reassembles each source (no relocation, every range identical to the original, every label at the address in its name, only the directive forms the generator writes: `.asciz`, `.string16`, `.long`, `.fill`, `.byte`, `.set`, `.org`) and `data_asm.py check` regenerates the source identically. The composer reports them as the class `tool_assisted_reconstructed_data`, apart from code, functions, index tables and padding; the map generator counts them as matched data. The directives are a textual form of the owner's data, the only data form permitted; the PE headers, import tables and resource directory stay `structured`, and no claim of original C provenance or of any meaning of a value is made. Machine-byte arrays in code, `incbin`, patching the original, and committing original code, data or resource bytes in any other form remain forbidden; the image composer (packet M02) may reference not-yet-reconstructed ranges from the local original at build time and must report them as referenced, never as matched. CRT, MFC and Vorbis code is reconstructed the same way and tracked as its own class.

Slice completion requires the packet's exact acceptance checks, pinned executable/code/native hashes, an independent review, and an explicit list of unverified branches. The integrator reruns meaningful combined checks before updating completion status. Do not mark the complete game done until both native gameplay and whole-file x86 matching pass.

## Function ledger

`outputs/blackmoor-decomp/function-ledger.json` gives every GAME.EXE function one status. `ported` is a reviewed claim, never an x86 match, and only a reviewed `port_acceptances` entry in `function-ledger-overrides.json` grants it; the ledger re-checks each entry mechanically. Library, CRT, MFC and Vorbis rule functions never count as ported (Vorbis only as `host_adapter_tested` under its parity rule).

- `native_oracle_verified`: one native symbol is the original function, a recorded oracle run executed every byte of it and compared the symbol, and a named test references the symbol.
- `native_oracle_verified_inlined` (rule FL-12, 2026-10-18; owner ruling on whether it counts as ported is pending): an original game function whose logic is inlined into a larger named native symbol. It counts only when all three hold: (1) a recorded oracle run executed every byte of the original and the oracle script drives the enclosing native symbol (or its module) and compares its effects; (2) that named symbol contains the function's logic, cites its address in the symbol's body or leading comment, and omits none of its observable behaviour; (3) an independent reviewer confirmed this for that function against the original, and the acceptance `note` (80+ characters) says where in the symbol the logic sits. The class is for game-region functions of game origin only. Counts report it as its own class next to `native_oracle_verified`.

## Testing

Keep testing proportional to risk. Do not turn small changes into testing projects.

- Add or extend tests for meaningful uncovered behavior, high-risk logic or regressions, not mechanically for every function or edit. Cosmetic and documentation changes normally need no new tests.
- Use the smallest reliable test: unit for isolated logic, integration for component interactions, E2E for critical user flows.
- Test observable behavior. Avoid duplicate tests, implementation-detail assertions, excessive mocks and tests written only to increase coverage.
- Reuse existing tests first. For bug fixes, confirm the regression test fails without the fix and passes with it when practical.
- Run the narrowest relevant checks while iterating. Broaden verification for cross-cutting changes and run the full suite before merge or in CI, not after every edit.
- Do not introduce testing frameworks or unrelated refactors unless requested.
- Never delete, skip or weaken tests merely to obtain a pass. Explain legitimate test updates and report what was and was not verified.
