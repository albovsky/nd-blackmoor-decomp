# First-scene media trace

The supplied game directory is the `game_dir` in `work/analysis/game-source.json`; paths below are relative to it. The boot evidence says state 14 loads `S0` (title `Player Challenge Screen`). `S0`, `S5900`, and `S4700` are type-3 resources in `Ciftree/CIFTREE.DAT`, not loose scene files. Extracting their payloads confirms these media names:

| --- | --- | --- |

The sound entries use Windows-style case-insensitive lookup (`ndsig` resolves to `Ndsig.his`). No `diff.avf`, `OPEN_A.avf`, or `toast.avf` is present, so these three scenes take the BIK branch. The CDVideo directory also contains 32 AVF files and 907 BIK files. The opening directory has further `EXT_OpnCin_ANIM2`–`ANIM5` BIK segments; the S4700 resource directly names the base clip, and this trace does not establish which later segments its actions reach.

## Original call path

- The existing boot trace maps state 14 to `S0`. Scene loading at `0x439822` calls `0x4163b4`, the single-frame video-stream opener, for the scene background. `0x4163b4` tests `.BIK` candidates before `.AVF` candidates. With `diff`, `OPEN_A`, and `toast`, the first existing candidate is the file under `CDVideo`.
- On the BIK branch, `0x4163b4` calls `0x4bf315` → imported `BinkOpen` in the shipped PE32 `binkw32.dll`; it gets dimensions/frame count through `0x4bee5f` → imported `BinkGetSummary`. Frame copy/advance helpers wrap imported `BinkCopyToBuffer`, `BinkGoto`, and `BinkNextFrame` (`0x4bf024`, `0x4bf19a`, `0x4bf10f`). The actual Bink codec is outside `GAME.EXE`.
- For S4700's movie action, `0x4cd6ff` selects the random-movie sequence and calls `0x4cdfd3` to open it. That routine also probes `.BIK` and `.AVF`; the BIK case creates the Bink movie path, while `0x4ce8ea` advances and copies Bink frames. The AVF movie case uses the in-game CChunk path and `0x4ce602` to consume decoded frames.
- AVF initialization at `0x414ceb` memory-maps the file, validates the `AVF WayneSikes` signature and version 2 header, then reads the 0x13-byte-per-frame chunk table. A representative file, `CDVideo/CON_GrennyPUZ.avf` (330,847 bytes), has that signature, 620×375 16-bit dimensions, and codec/control byte 2 at offset `0x20`. The reader thread `0x4cf687` calls `0x41546f` (single-frame chunks) or `0x4156ea` (double-frame chunks). Their decode path reaches the counter-obfuscated LZSS routine `0x415db9` and the AVF type-1/type-2 command/delta expansion at `0x416af3` (with fill helper `0x43ef77`).

## S0 background bounds

The case-sensitive installed asset is `/Applications/Nancy Drew - Curse of Blackmoor Manor.app/Contents/Resources/game/Nancy Drew Curse of the Blackmoor Manor.app/Contents/Resources/drive_c/GOG Games/Nancy Drew - Curse of Blackmoor Manor/CDVideo/diff.bik` (102,732 bytes). The Bink summary path at `0x4163b4` sets the full source crop to `[0,0,width-1,height-1]`; `diff.bik` is 620×375, so its inclusive source rectangle is `[0,0,619,374]` and its local frame-copy origin is `(0,0)`.

The 48-byte BOOT `VIEW` record is copied to globals starting at `DAT_00583186` by `0x435015`. Its signed little-endian rectangle tuples are `(10,10,629,384)`, `(0,0,619,374)`, and `(0,0,619,374)`. At `0x439822` / `0x43a4xx`, the scene loader stages `VIEWPORT_AVF` with a pointer to tuple 2 first and tuple 1 second. The configured screen destination is therefore inclusive `[10,10,629,384]` (620×375), exactly matching the Bink source size; inclusive width is explicitly calculated as `(right-left)+1` at `0x435015`. The video-dimension checks at `0x439822` also match tuple 3. This establishes top-left `(10,10)`, not `(10,11)`.

## Engine/codec boundary and native first-frame adapter

`GAME.EXE` is PE32 x86 and its import table names `binkw32.dll` directly. The imports include `_BinkOpen@8`, `_BinkGetSummary@8`, `_BinkDoFrame@4`, `_BinkCopyToBuffer@28`, `_BinkNextFrame@4`, `_BinkGoto@12`, `_BinkWait@4`, `_BinkSetSoundSystem@8`, and `_BinkOpenDirectSound@4`. The installed PE32 x86 DLL exports these APIs and additional Bink buffer/surface/YUV blit functions. This places original scene/runtime behavior in `GAME.EXE`, while BIK parsing, decompression, and Bink's host surface/audio path are delegated to the external Bink DLL. A matching-engine track should retain those original API call boundaries; using FFmpeg on macOS is a port adapter, not evidence that the engine implemented the Bink codec itself.

The host has ARM64 FFmpeg 9.0.1 (`/opt/homebrew/bin/ffmpeg`) with `binkvideo`, `binkaudio_dct`, and `binkaudio_rdft` decoders. The official FFmpeg source has a Bink video decoder and a Bink demuxer, and the official API example demonstrates in-process demux/decode; the adapter uses those public libraries rather than shelling out or copying decoder implementation ([FFmpeg Bink decoder](https://github.com/FFmpeg/FFmpeg/blob/master/libavcodec/bink.c), [Bink demuxer](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/bink.c), [libavformat/libavcodec API example](https://ffmpeg.org/doxygen/trunk/demux_decode_8c-example.html)).

`src/bink_adapter.[ch]` supplies a bounded native host adapter for exactly one first video frame from a local Bink video file. It uses libavformat/libavcodec/libswscale directly, limits input files to 256 MiB and dimensions to 4096×4096, requires Bink video, disallows non-file protocols, and returns caller-owned RGBA bytes. `scripts/build_bink_adapter.sh` builds an ARM64 dylib; `tests/test_bink_adapter.py` checks the real `diff.bik`, `OPEN_A.bik`, and `toast.bik` images against FFmpeg CLI RGBA output and checks missing, corrupt, and URL inputs. All three frames are 620×375 and byte-match the CLI outputs (SHA-256 values are printed by the test). This proves the adapter matches the installed FFmpeg build for these samples, not the proprietary Bink DLL's pixels or byte-for-byte output. It does not yet handle cinematic frame timing, sound, scene integration, or ship FFmpeg libraries. The current Homebrew FFmpeg dylibs are ARM64, declare macOS 27 as their minimum, and are built with GPL/version-3 options; the adapter currently links to absolute Homebrew dylib paths. Packaging therefore needs a compatible FFmpeg build and a deliberate dependency/licensing configuration; other macOS releases require a dependency set built for their deployment target.

## Decoder scope and oracle candidates

For the first visible scenes, the next native media milestone should decode Bink `BIKi` video frames for the three one-frame assets. The opener then requires multi-frame Bink timing and Bink DCT audio; `S0` sound also needs the HIS wrapper plus Vorbis for its named audio. This first path is therefore not unblocked by AVF support alone. The game-side AVF algorithms are a separate, comparatively direct recovery target for the many AVF assets.

Best in-executable original-x86 oracle candidates for AVF are `0x415db9` (compressed-frame output) and `0x416af3` (delta/tile expansion); both are buffer-driven and avoid Windows I/O. `0x43ef77` is a small pure fill helper. Pixel-format conversion `0x4c7314` is already matched over 720,896 word cases in the existing validation. `0x414ceb` is not a pure oracle target because it calls Windows mapping APIs. For BIK, no codec routine is present in the game EXE: an original-behavior oracle would need to isolate the shipped `binkw32.dll` API and its frame/surface inputs rather than call a pure game routine. The FFmpeg adapter is suitable as a native first-background port milestone, while the matching track records the original DLL call sequence. Keep it separate from full Bink audio and cinematic playback.
