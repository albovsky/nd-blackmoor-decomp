# image/: structured description of GAME.EXE

Sources for the M02 whole-file composer (`scripts/compose_image.py`). Nothing here is an original code, data or resource byte dump: the files hold PE field values, import names and hints, resource tree shape, switch-table targets and hashes. The only literal bytes are the 14-byte standard Microsoft linker DOS stub in `layout.json` (boilerplate in every LINK-produced PE).

| File | Content | Class produced |
|---|---|---|
| `layout.json` | DOS header, Rich tuples (key recomputed, not stored), PE/optional header, data directories, section table, code regions, zero fill | structured: `dos_header`, `rich_header`, `pe_headers`, `section_table`, `header_padding`, `section_padding` |
| `imports.json` | 13 DLLs, 326 symbols with hints and RVAs | structured: `import_directory`, `iat` |
| `resources.json` | ID-only resource directory tree (38 leaves), leaf RVA/size/codepage, zero fill | structured: `resource_tree`; leaf payloads are bound from the audited data source `data-002` (`data_batches`) |
| `text_data.json` | switch jump tables (code addresses), 0xCC span padding; byte index tables by extent only | structured cross-check only: `jump_tables`, `int3_padding` (the composed bytes come from the audited `.s` data items and data batch `data-005`); index table bytes are bound from the audited `.s` data items |
| `reconstructed.json` | reviewed matching manifests (`bindings`), the audited tool-assisted assembly batches of M03 (`asm_batches`) and the audited data sources of packet M-C (`data_batches`) bound as reconstructed ranges | reconstructed (provenance classes reported separately) |
| `ranges.json` | every remaining range: offset, length, SHA-256, kind, region, name | referenced |
| `coverage-report.{json,md}` | snapshot of the composer's report | |

`ranges.json`, `text_data.json`, `layout.json`, `imports.json` and `resources.json` are produced by `compose_image.py derive` from the local original and `function-index.json`; `reconstructed.json` is hand-written; `ranges.json` is re-derived after any change to it. A test re-runs `derive` and requires byte-identical output.

## Commands

```bash
python3 outputs/blackmoor-decomp/scripts/compose_image.py build     # compose, require the whole-file SHA-256
python3 outputs/blackmoor-decomp/scripts/compose_image.py stages    # enable structured groups one at a time, re-check the hash
python3 outputs/blackmoor-decomp/scripts/report_image_coverage.py   # the Track M progress number
python3 -m unittest outputs/blackmoor-decomp/tests/test_compose_image.py
```

The composed file and the full report are written under `outputs/blackmoor-decomp/build/image/` (git-ignored).

## Tool-assisted assembly batches (`asm_batches`)

Each entry names an `asm/batch-NNN.json` manifest and its audit report. At build time the composer requires the report to be all-accepted for exactly that manifest (hash match), reassembles every function's `.s` with the pinned `i686-w64-mingw32-as` 2.43.1 (version line plus the self-test of `audit_tool_assisted.py`), requires zero relocations, and requires the symbol's bytes to hash to the code SHA-256 the manifest records for the original code part. The bytes placed in the image are the assembled bytes. Bindings listed under `bindings` win on overlap, so the 11 S08 functions and the 2 incomplete C ranges stay in their own classes and are reported as superseded. Data items of these functions are bound as reconstructed data in their own provenance classes: the audited switch tables (`SWTAB_<va>`, `tool_assisted_reconstructed_jump_table`), the index tables (`IDXTAB_<va>`, `tool_assisted_reconstructed_index_table`) and all padding (`PAD_<va>`: 2,214 bytes of `int 3` and 1,526 of alignment instructions, `tool_assisted_reconstructed_padding`); a switch table or `int 3` fill that a structured group also describes replaces that structured item (`supersede_structured`), the group stays a cross-check, reassembled and hash-checked like the code, never counted as functions or code bytes (the 1,464 padding bytes were typed code in `ranges.json` before, so the code total fell from 1,203,014 to 1,201,550 bytes and about 0.12 points of the rise in the reconstructed code fraction are the smaller denominator, not new coverage; the "functions" count includes the 554 derived entries, which are exactly reproduced code, not proven functions). `asm/batch-009.json` holds the derived entries (code the span split found that `function-index.json` does not list). `asm/batch-010.json` holds the last 22 code fragments (56 entries: 13 call-ends, 7 fall-throughs and the 36 code runs of the two CRT block copies), counted under the owner ruling of 2026-10-16 only bound together with the range that follows them; with it every one of the 1,201,488 code bytes is reconstructed and none is referenced (the 62 bytes of nop padding in those entries are in `tool_assisted_reconstructed_padding`, so the code denominator fell from 1,201,550 to 1,201,488).

## Replacing a referenced range

1. Add the reviewed object (M03 `tool_assisted_reconstructed_assembly` or a hand-reviewed `explicit_reconstructed_assembly_source`) and bind its manifest in `reconstructed.json`.
2. Remove the covered bytes from `ranges.json` (re-run `derive`, which carves bound ranges out of the referenced list).
3. `compose_image.py build` must still print the original SHA-256; `report_image_coverage.py` shows the new generated/referenced split.

The composer rejects overlapping ranges (a function and a data item claiming one byte), missing bytes, and a referenced range whose SHA-256 differs from the description.

## Data batches (`data_batches`, packet M-C)

Each entry names an `asm_data/data-NNN.json` manifest and its audit report (`scripts/data_asm.py`, owner ruling of 2026-10-19). At build time the composer requires the report to be all-accepted for exactly that manifest (hash match), regenerates the full source from the local original (it is never committed: the repository keeps the manifest, report and the payload-free layout `data-NNN.layout`), requires its SHA-256 to equal the manifest's and its masked form to equal the committed layout, reassembles it with the pinned `i686-w64-mingw32-as` 2.43.1 (version line plus self-test), requires zero relocations, and requires every range's assembled bytes to hash to the SHA-256 the manifest records for the original range. The bytes placed in the image are the assembled bytes, in the provenance class `tool_assisted_reconstructed_data` (reported apart from code, functions, index tables and padding). `data-001` binds `.rdata` 0x12a54c-0x134910 and `.data` 0x137000-0x16a000 (250,820 bytes), `data-002` the 22 resource payload runs (24,156 bytes). `ranges.json` is empty after the re-derive: no range is referenced any more, and a range that is both bound and referenced fails the overlap check. Batches `data-003` (18,914 bytes: file headers, `.text` zero fill, IAT, import directory and `.rdata` padding) and `data-004` (4,516 bytes: resource directory tree and padding) have the manifest profile `structures`: they cover the 23,430 bytes the structured groups `dos_header`, `rich_header`, `pe_headers`, `section_table`, `header_padding`, `iat`, `import_directory`, `resource_tree` and `section_padding` also generate. The composer still generates those groups from the descriptions in this directory and compares them with the original (`structured_mismatches`), then places the audited batch bytes instead of the structured items inside a `structures` range (an item straddling the edge of a range is an error; `structured_replaced_by_audited_sources` in the coverage report counts them). Batch `data-005` (profile `jump_tables`, 240 bytes in 12 ranges) covers the 14 jump tables between the code runs of the two CRT block-copy routines (`0x0050ed50`, `0x0050fa90`), which belong to no audited function source because the fragment generator cuts those spans at the tables; it is generated and audited like the others (`.long CODE_<va>` case addresses as named constants), lies inside `.text` and is reported in the class `tool_assisted_reconstructed_jump_table`. Since it was bound no structured item is placed any more: the composed image has 0 structured bytes, and `structured_replaced_by_audited_sources` counts the 1,039 structured items (31,500 bytes) the audited sources replaced. The structured groups are still generated from the descriptions and compared with the original first (`structured_mismatches`).
