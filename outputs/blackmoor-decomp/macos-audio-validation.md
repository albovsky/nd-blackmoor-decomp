# Native macOS PCM audio adapter validation

The native host adapter lives in `outputs/blackmoor-decomp/src/macos_audio.h` and `.mm`. It accepts finite interleaved float PCM, copies each play request into an owned `AVAudioPCMBuffer`, and routes one `AVAudioPlayerNode` per slot into the `AVAudioEngine` main mixer. The source format is explicit per player so the mixer converts differing source rates and channel counts; reusing a slot with a different source format reconnects its player after stopping the prior generation.

Output mode creates the engine without starting it and starts it on the first play. Offline mode configures `AVAudioEngineManualRenderingModeOffline` before accessing engine I/O or mixer nodes, then renders through that same player-node/mixer graph. The offline test never uses an audio output device and never produces audible sound. Output playback clears a slot at AVFAudio's `DataPlayedBack` boundary; offline mode uses `DataRendered` because its manual graph has no output route. Each callback captures weak host state, a slot ID, and a generation, then updates only the still-current slot generation. The host API itself is main-thread-only, while callback state updates are mutex-protected.

Build verification passed on macOS 27.0.1 arm64 with the macOS 27.0 SDK. `scripts/build_macos_audio.sh` built an arm64 dynamic library with Apple Clang, C++17, ARC, `-Wall -Wextra -Wpedantic -Werror`, targeting macOS 27.0 and linking AVFAudio/Foundation.

`python3 outputs/blackmoor-decomp/tests/test_macos_audio.py` has now passed three consecutive scoped unsandboxed runs, with all six tests passing each time. They cover input-buffer ownership, stereo sample order and gain, concurrent slot mixing and gain changes, stop-to-silence, loop continuity, offline rendered-completion state, stale-completion generation protection, 24 kHz to 48 kHz conversion, reconfiguring a slot to another sample rate, invalid arguments/non-finite samples, main-thread enforcement, and output-mode/manual-render separation. The same command inside the sandbox passed the output-mode/argument test and skipped the five offline graph tests because the restricted process could not query the AudioComponent registrar (`required condition is false: comp != nullptr`). The scoped unsandboxed runs exercised AVAudioEngine's real manual-render graph successfully; no hardware playback was used.

The API's gain is a caller-provided linear amplitude in `[0,1]`. The adapter does not claim DirectSound volume-curve compatibility or establish the game's gain mapping. Output `is_playing` clears after AVAudioPlayerNode's `DataPlayedBack` callback; offline `is_playing` clears on `DataRendered`, the observable manual-render boundary. No audible hardware playback was verified. Spatial positioning, panning rules, fades, device-route changes, interruption handling, and original-engine parity have not been established. These tests use generated PCM and do not read or modify original game assets.

API declarations and behavior were checked against the installed Apple AVFAudio SDK headers: `AVAudioEngine.h` documents offline manual rendering without an audio-device connection and `renderOffline`; `AVAudioPlayerNode.h` declares both `DataPlayedBack` and `DataRendered`, describes their playback/render callback boundaries, and assigns callback thread-safety to the client; the same header declares `playAndReturnError`, and `AVAudioEngine.h` declares the error-returning graph connection method.
