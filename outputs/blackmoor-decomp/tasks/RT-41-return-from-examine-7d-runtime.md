# RT-41: raw 0x7d return from the examined item's scene

Owner thread: Claude Sonnet (cloud). Follows RT-39 and RT-36. After PR 102, 2,027 of 2,078 scenes had every action type handled. Raw 0x7d (4 rows, 4 scenes) was the next on the ranked list after 0x1b (RT-40, another thread) and unblocks all 4 (2,027 to 2,031). It was left out of RT-39 because it calls an object method (`0x4eb5f2`).

## The original (GAME.EXE, SHA-256 afd337a2...5c45)

* Loader arm `0x40e61e` of `0x40b34a` (A-7D.1; `src/action_family_7d.c`): one body byte is copied; the dependency tail follows. The byte is never read afterwards.
* Dispatcher `0x427a50`, arm `0x42950b..0x429556`, gate mode 0 (`0x423f57(deps, 0)`). For a true gate the arm calls the inventory view method `0x4eb5f2` (thiscall on `0x571442`, no arguments), stores the word `0xffff` into `0x583f1d` (`0x429539`) and sets the row's completion byte `[0x5bb625 + row * 0x8d] := 1` directly (`0x42954f`). Like 0x6e/0x6f: the generic completion `0x42ba3a` and the dependency reset `0x423d33` never run, whatever the subtype, and the phase word is untouched: executor disposition `DIRECT_COMPLETED` with the phase it was given.
* The method `0x4eb5f2` is the pop that pairs with the saver `0x4eb70f` (called from the inventory examine branch `0x4ea269`, which stores the examined item's scene) and works on the second of the three "return to this scene" records, `0x5c3a1b..0x5c3a30` (initialised by `0x437011..0x43703b`: marker and scene 9999, words 0, 0, type word 2). In order: (1) `movsx word [0x5c3a1b] == 9999` is the empty test; with the debug flag `0x63a4cd` set it logs through `0x52139c`, then stores 0 into `[0x5c3a1b]` and carries on (it is NOT a fatal path, unlike `0x42e493`); (2) `[0x5bb57b] := [0x5bb57f] := movsx word [0x5c3a1d]`, `[0x5bb599] := word [0x5c3a1f]`, `[0x5bb595] := word [0x5c3a21]`, `[0x5bb59b] := dword [0x5c3a25]`, `[0x5bb59f] := dword [0x5c3a29]`, `[0x5bb5a3] := dword [0x5c3a2d]`, `[0x5c39ff] := 1`, `[0x5bb1ca] := (movsx word [0x5c3a23] == 1 ? 0 : 1)`; (3) when `movsx word [0x583f1d] != -1` the inventory add step `0x4e9e84(item, 0)` (flag 0: no sound, no UI, ends with the view rebuild `0x4e812f`) and then the UI animation `0x4e0559(1, 0, 0)` on the task bar object `0x570508`, also when the add found a duplicate; (4) `[0x583999] := 4` (engine mode: scene change), `[0x5c3a1b] := [0x5c3a1d] := 9999`; (5) when byte `[0x571442 + 0x7011]` is 0, byte `[0x583232] := 1` (the task bar inventory flag, consumed by the next tick's `0x43a7ca`). The saver `0x4eb70f` (one stack argument whose low word becomes `[0x5c3a23]`) copies the running scene's words like `0x42e560` does and has the same quirk: it stores `0x5bb5ab` into `0x5c3a29` and overwrites it with `0x5bb5af`, so `0x5c3a2d` is never written.
* The dispatcher loop head requires mode 3 at every row (`0x427a8e`), so after the visit no later row of the same pass runs; the executor's transition request stops the pass the same way.
* Corpus (decoded scene resources): 4 scenes, 4 rows, all subtype 1, body byte always 0, three of them with a dependency record.

## Native implementation

`src/action_family_7d_runtime.[ch]`: the record (`SceneRestoreSlot`, init words, the saver `scene_restore_slot_save`), the pop `scene_restore_slot_pop` (steps 1, 2 and 4; reproduces the original on an empty record, where it carries on) and `action7d_visit` (the whole arm: pop on a copy, the add step through `action78_add_item(item, 0, ...)` of RT-19, the UI request `(1, 0, 0)`, the scene change, the inventory request, then the record commit, selector `-1` and completion; every rejection before any effect, a provider failure after earlier effects is `ERR_HOST` without rollback, as in the original). `src/session_bindings_a7d.[ch]`: one binding (`DIRECT_COMPLETED`, phase unchanged; the empty record is `HANDLER_ERROR` before any effect, a missing provider `UNSUPPORTED`; the inventory model is read at every visit so the view mode and flag stay live). Registration `bindings[37]` in `src/blackmoor_app.mm` (count 38; slot 36 is RT-40, raw 0x1b), the module pair in `scripts/build_native_app.sh`, `scripts/build_action_family_7d_runtime.sh`. In the app the record is a new `scene_restore_slot`, the selector is `new_game.opaque_selector` (0x583f1d), the add and the UI request reuse the raw 0x78 providers, the scene change is the raw 0x6f one, and the inventory request sets `bar.flag[TASKBAR_BUTTON_INVENTORY]` (byte 0x583232); the view bytes come from the UIIV layout (loaded before the visit).

## Verification

* `tests/action_family_7d_runtime_test.c`: 11 unit cases (record fields, sign extension, start flag, empty record, saver round trip, visit with and without an item, duplicate, item 0, every failure path, binding dispositions and request, binding failures; ASan/UBSan clean); `tests/test_action_family_7d_runtime.py` runs them plainly, under sanitizers and under 30 source mutants (the host-status mapping, provider requirements and ordering the oracle cannot reach).
* `tests/action_family_7d_runtime_original_oracle.py` (+ `_oracle_driver.c`): the real dispatcher `0x427a50` runs the rows under Unicorn with the real gate, the real method `0x4eb5f2`, the real add step `0x4e9e84` and the real `0x4e0559`; the rebuild `0x4e812f` is replaced by a logger (its own oracles are RT-19/RT-22) and the sound request `0x4fb2e3` is guarded. Against the native binding it compares: the open rows that entered the arm and the one method entry, the add calls (item, flag 0), the rebuild calls with the whole inventory at that moment (held, count, all 70 list words, all 70 presence dwords), the UI animation call (this `0x570508`, 1, 0, 0), the order of those calls, the completion byte and phase of every row, the 22 record bytes, the selector, held word, count, list and presence, the view bytes, byte-for-byte memory windows seeded with random bytes around every destination global (`0x583232` included), the scene-change request, and that neither `0x42ba3a` nor `0x423d33` ran. Direct calls compare the saver `0x4eb70f` and the method `0x4eb5f2` against `scene_restore_slot_save` and `scene_restore_slot_pop` on random records and sources, empty records included. View modes `(mode, slot flag)` cover the item-first and item-last layouts. See the receipt numbers in COORDINATION-STATUS.md.
* `tests/action_family_7d_runtime_corpus.c`: all 4 corpus rows through the binding with the decoded scenes.

## Limits

* The macOS glue (`blackmoor_app.mm`) is not compiled or run in the cloud.
* An empty record is a tagged expected difference: the original carries on and requests scene 9999 (and still re-adds the item); the native handler refuses it (`HANDLER_ERROR`, nothing changes). The record is filled only by the saver `0x4eb70f`, which the inventory examine branch `0x4ea269` calls (not ported, RT-22 stops at that branch), so in the app a 0x7d row currently reports this blocker until examine is ported. The saver itself is ported and oracle-checked.
* The view rebuild `0x4e812f`, the effects of `0x4e0559` (the UI button cells and the bar object counter) and the main loop's consumer of `0x583232` are host requests, not compared byte for byte. The native refuses inventory states the original would overflow (a full list, an item outside the presence array); the oracle compares only the domain where both run.
* The oracle builds the rows in memory (the scene loader `0x40b34a` is not run) and replays the 4 corpus rows with and without a stand-in dependency record. The debug flag `0x63a4cd` is modelled as 0.
