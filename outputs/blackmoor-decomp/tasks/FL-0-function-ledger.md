# FL-0: GAME.EXE function ledger (plan, schemas and work split)

Owner request (Glib, 2026-10-14, via the coordinator): every function in GAME.EXE gets exactly one status, `ported` (with a pointer to the native code or test that covers it), `not_needed` (with a reason such as Win32-only, CRT/library or debug) or `pending`, and a "Function ledger" panel on the progress map shows the counts. Default classification is conservative: anything unproven is `pending`, never `not_needed`. Plan written at Opus high; implementation by Claude Sonnet (high) `slice-implementer`s; one independent `slice-reviewer`; root integrates. The goal is a completeness proof for the native port that does not depend on the whole-file x86 match: code no scene action reaches directly (save/load, menus, timers, input, audio, caches) must be accounted for too. The ledger never claims more than the evidence supports: `ported` is a reviewed claim that native code or a test demonstrably covers that function's behaviour, and it is a different class from the x86 match track (`asm/`, `matches*.json`).

Name the feature the *function ledger* everywhere. `decomp-progress/generate.py` already has a `--ledger` option and the `blackmoor-range-ledger/1` format for the whole-file range ledger; do not touch or reuse them.

## Evidence surveyed by the planner (verify, do not trust)

- Universe: `function-index.json` has 4,188 function starts (`address`, `name`, `file`, `evidence_id`; no sizes). By `decomp-progress/layout.json` region: game 2,507, vorbis 178, crt_mfc 1,503; that crt_mfc count includes 557 `Unwind@` and 13 `Catch@` exception funclets that belong to game functions. `asm/census-summary.json` splits spans into 4,752 functions (564 derived parts, 7 fall-through fragments, 2 unsplit CRT spans). The private Ghidra dump `work/analysis/m0/fable-census/functions.jsonl` has body sizes and 22 `thunk:true` import thunks that sit inside other functions' spans (for example inside the span of 0x4fce90).
- `src/*` cites 524 distinct addresses; only 230 are indexed function starts (the rest are interior addresses, data or IAT). Citation style varies.
- Private receipts `work/analysis/slices/*handoff*.json` (gitignored) carry about 1,325 code windows in at least four shapes (`start/end`, `start/end_exclusive`, named dicts, `[int,int,sha]` lists; some `(va,size,sha)`), plus `independent_review`, `unverified_branches`, `deliberate_safety_rejections`, `hook_inventory`, `files`. About 333 functions have any automatic evidence; only about 76 have both a source citation and a full-window receipt. Oracle windows cover more than they test (for example 0x40b34a..0x410ca4 maps the loader but each A-* oracle runs one arm; 0x424aa8..0x425b8b covers the dependency loader but slot reuse and tree construction are not modelled).

## Files and data model (frozen interface)

| File | Kind |
|---|---|
| `outputs/blackmoor-decomp/function-evidence.json` | Generated by `scripts/extract_function_evidence.py` from private receipts, committed oracles and `src/`; sanitized: addresses, paths, hashes, no original bytes |
| `outputs/blackmoor-decomp/function-xrefs.json` | Generated by `scripts/extract_function_xrefs.py`: per start the Ghidra body size, derived parts, direct callers/callees (VA pairs), imported API names called, has-data-reference flag, EH-funclet parent, thunk flag |
| `outputs/blackmoor-decomp/function-ledger-overrides.json` | Hand-maintained: `port_acceptances`, `not_needed_entries`, `not_needed_rules` (each with predicate id, rationale, accepted sample review), `semantics_sensitive` |
| `outputs/blackmoor-decomp/function-ledger.json` | Generated ledger, `schema: "blackmoor-function-ledger/1"`, one entry per line, sorted by VA |
| `decomp-progress/function_ledger.py` | Pure derivation and strict validator (standard library only) imported by the generator and the CLI |
| `scripts/build_function_ledger.py` | CLI: `--write` and `--check` |
| `scripts/sample_function_ledger.py` | Deterministic reviewer sampling (seed = sha256 of the inputs) |

Ledger top level: `schema`, `original_sha256`, `inputs` (`[{path, sha256, role}]`, every file read, including each src/test file an evidence pointer names), `counts` (by status, class, region, reason), `entries`.

Entry fields: `va` (hex string), `name` (Ghidra label, informational, never evidence), `span` (bytes to the next indexed start, or to the end of `.text` 0x52925a), `body_size` (Ghidra size or null), `derived_parts` (list of VAs), `region` (`game|vorbis|crt_mfc`), `origin` (`game|library|compiler_eh|import_thunk|unknown`, set only from xrefs evidence), `seam` (true if within 0x400 bytes of a region boundary), `status` (`ported|not_needed|pending`), `class` (for ported: `native_oracle_verified|native_tests_only|host_adapter_tested`; for not_needed: `nn_rule|nn_reviewed`; for pending: `candidate_port|partial_native|static_navigation_only|none`), `x86_match` (`null` or `{provenance, complete, manifest}`; orthogonal, never feeds `status`), `evidence` (list of pointers: `native_source {path, symbol, sha256}`, `oracle {path, window:[start,end_excl], window_sha256, use: entry|callee|mapped, sha256}`, `test {path, test_id, sha256}`, `receipt {slice, path (work-relative), sha256, review}`, `mention {path, symbol|null}` with no line numbers), `blockers` (unverified items whose address falls in the span), `divergences`, `reason {code, text, rule}`, `review {reviewer, date, sample}`.

## Classification rules, in order (any conflict fails generation)

1. Universe: exactly the 4,188 index starts; spans sum to 1,213,018; an override naming a non-index VA or the same VA twice is an error.
2. Address resolution (extractor): only an exact function start is a citation; interior addresses become a `mention` on the containing function; addresses at or above 0x52925a are counted `unresolved` and dropped; M03-derived starts map to the parent's `derived_parts`. Window shape is settled by hashing the local original (path from `work/analysis/game-source.json`): exactly one reading of a window must reproduce its recorded sha256, otherwise the extractor fails. Only hashes are published.
3. Port acceptance: a function is `ported` only through a reviewed `port_acceptances` entry (`va`, class, pointers, reviewer, date) that the generator re-checks mechanically and fails closed on: (a) the VA appears in the named C symbol's body or leading comment (use `playable.py`'s `function()`/`braced()` scanner); (b) a named test exists and references the symbol or module; (c) for `native_oracle_verified`, an oracle window covers `[va, va+body_size)` with use `entry` or `callee` (taken from receipt hook lists; `mapped` windows never qualify); (d) no blocker remains unless listed under `divergences` and recorded as a deliberate safety rejection; (e) every derived part is itself accounted for. `host_adapter_tested` applies to Win32/library behaviour replaced by an adapter with a contract test (for example the CRT `rand` port in `src/session_bindings_conditions.c`).
4. Per-function `not_needed_entries`: reason code from the closed enum `win32_plumbing_no_observable_effect | crt_startup_termination | library_internal_unreached_by_game | host_libc_standard_contract | debug_diagnostic_only | unreachable_no_refs | compiler_eh_funclet`, each with a machine precondition checked against xrefs (for example `unreachable_no_refs` needs zero callers and no data reference; `win32_plumbing...` needs imports within a reviewed allowlist and no game-region callee that is pending or ported). Every game-region `not_needed` is per-function; no rule may cover game code.
5. `not_needed_rules`: predicate id implemented in `function_ledger.py`, rationale and accepted sample review `{sample_sha256, n, defects: 0}`. Rules always exclude seam functions, anything with a src mention or a receipt, anything in `semantics_sensitive` (rand, `__ftol`, printf/float formatting, qsort, time, file I/O, malloc failure) and library functions with a path back into game code. Candidates: R-EH (`Unwind@` funclets whose parent is natively ported or has no native C++ exception path; needs an owner/reviewer ruling; the 13 `Catch@` funclets are reviewed one by one) and R-LIB-INTERNAL (CRT/MFC functions not transitively called from game code).
6. Vorbis: all 178 functions stay `pending` until a PCM-parity test compares the original Vorbis x86 against the FFmpeg path.
7. Defaults: `pending`, class `candidate_port` (full window plus citation), `partial_native`, `static_navigation_only`, else `none`. A Ghidra name is never evidence.

## Progress-map panel

`generate.py` loads `function_ledger.py` like it loads `playable.py` and adds `model["function_ledger"]`: strict schema validation, re-derivation from pinned inputs, and on any difference `error: function ledger stale; rerun scripts/build_function_ledger.py --write`. REPORT.md gets a "Function ledger" section. `template.html` gets `<section id="ledger">` after `#playable` and before `#bars` (hidden when there is no ledger): metrics Ported (oracle-verified / tests-only / adapter), Not needed (by reason), Pending (by subclass); a stacked status bar per region; a cross-tab (x86-matched functions and how many are natively ported); a table with status, region and class filters, address search and paging; relative links to `../src` and `../tests`, private receipts shown only as name plus sha256. Caveats on the page: ported is a reviewed claim, not an x86 match; tests-only is weaker evidence; spans include tables, padding and thunks; region seams are accurate to a few hundred bytes; private receipts are not re-hashed when the page is built. Store compact rows (`[va, span, region_i, status_i, class_i, ev_i]`) so 4,188 rows stay small.

## Risks and containment

Overclaiming ported (reviewer/date required, full-body window with entry/callee use, blockers from `unverified` lists, tests-only and adapter classes reported separately, x86 match kept orthogonal); thunks, stubs and data in code (`body_size` plus `derived_parts`; the 0x4fce90 span counts as ported only if its seven thunks are accounted for; the 2 unsplit spans and 7 fall-through fragments stay pending); address aliasing (exact starts only, interior addresses are mentions, shape ambiguity resolved by hash, worktree paths normalized); region mislabels (`origin` from evidence, `seam` excludes from rules); library semantics trap (`semantics_sensitive`); staleness (every input pinned by hash, generator refuses on any difference, output sorted one entry per line); manual volume (rules plus deterministic sampling; expect more than 80% pending at first publication and say so on the panel).
